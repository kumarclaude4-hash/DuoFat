# ─────────────────────────────────────────────────────────────────────────────
# Baseline profile — cold-start critical path.
#
# AGP packages this file into the APK as a baseline profile; androidx.profileinstaller
# (declared in app/build.gradle) installs it shortly after first launch so ART AOT-compiles
# these methods instead of interpreting them on every cold start.
#
# Rule syntax:
#   H  = "hot"      — called often, compile it
#   S  = "startup"  — on the startup path
#   P  = "post-startup"
#   L<class>;-><method><signature>
#   ** wildcards match any characters including '/', so `->**(**)**` means every method.
#
# SCOPE AND HONESTY ABOUT IT
# This profile is hand-written from the startup call graph (DuoShieldApp -> SplashActivity ->
# LockScreenActivity/SignInActivity -> ConversationListActivity), not generated by running the
# app. A hand-written profile is a real improvement over having none — the classes below are
# unambiguously loaded and executed on every launch — but it is strictly worse than a measured
# one, which captures the actual hot methods inside library code (Firebase init, Room/SQLCipher
# open, Glide setup, RecyclerView first layout) that dominate startup and that no human can
# enumerate accurately by reading source.
#
# To replace this with a measured profile, add a :baselineprofile module using the
# androidx.baselineprofile Gradle plugin, write a MacrobenchmarkRule startup journey, and run
# it on a device or Gradle Managed Device; the generated file then supersedes this one. That
# needs a real device/emulator and new Gradle plugin + dependency entries in
# gradle/verification-metadata.xml, which is why it is not done here.
#
# Class-level wildcards are used rather than per-method rules on purpose: these classes are
# small, entirely startup-scoped, and a wildcard cannot silently drift out of date when a
# method is renamed the way an explicit signature can.
# ─────────────────────────────────────────────────────────────────────────────
